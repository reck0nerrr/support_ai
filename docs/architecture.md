# Архитектура Support Copilot

POST /triage, make predict и CRM вызывают один движок в engine.py через triage.run_triage. contract.py описывает официальный запрос/ответ. Старые категории CRM преобразуются явным адаптером; полная классификация сохраняется в analysis.result.triage. Изменять существующие таблицы CRM для новой таксономии не потребовалось.

## Обработка

1. В HTTP принимаются только входные признаки и сообщения player/reported_player. Для исторического JSONL parse_export удаляет ответы admin и исходы до сериализации промпта.
2. Сохраняется исходный текст; отдельное нормализованное представление восстанавливает казахские буквы из замен cp1251. lang/server_lang — подсказки, язык определяется по тексту.
3. RAG локально ранжирует пункты BM25 с расширением RU/KK/UZ-запросов. Выбирается до RAG_TOP_K источников в пределах RAG_MAX_CHARS, без обрезания пункта посередине. Номер игрока — слабая подсказка, не готовый ответ.
4. Один Responses API вызов со строгой JSON Schema генерирует категорию, приоритет, черновик и причины. Админские ответы из handout в inference не используются. Offline выдаёт явный резервный ответ и эвристические признаки.
5. Сервер проверяет источники, номера, маркеры, URL и ряд опасных обещаний, пересчитывает извлечённые признаки и применяет обязательную передачу человеку. Проверки не заменяют семантическую оценку человеком.
6. Каждая попытка записывается в triage_runs: usage, тариф, стоимость, задержки, версия промпта/корпуса, найденные источники, безопасная ошибка. При известном usage отклонённая генерация также учитывается в расходах.

## Данные

handout.py импортирует только пять ожидаемых файлов в private/handout. Они исключены из Git, в Docker доступны read-only. rules.json — основной корпус, в том числе справка RP; ключ правила содержит идентификатор раздела и номер. taxonomy.json задаёт 14 категорий. Предложения шаблонов из train формируются prepare.py отдельно и не попадают в базу знаний без проверки.

Оригинальные изображения/игровые логи отсутствуют. has_evidence означает наличие вложений по метаданным, claims — слова игрока, verified_facts в CRM всегда пуст. Никаких инструментов наказания, платежей или восстановления аккаунта у движка нет.

## CRM и очередь

Сессия сотрудника хранится в HttpOnly cookie, операции защищены CSRF и серверными правами. Просмотр обращений ограничен сервером/ролью. Worker использует PostgreSQL SKIP LOCKED, проверяет ревизию контента перед применением результата. Редактирование, утверждение и эскалация сохраняются в журнале; ревизии не позволяют отправить устаревший автоответ. Отправка Telegram не повторяется при неоднозначном результате. Токен Telegram не выводится в HTTP INFO-логах worker.

Дневная/платёжная квота не повторяется автоматически. Короткие временные отказы учитывают Retry-After. Batch ограничивает максимальное ожидание и сохраняет явные ошибки вместо многочасового зависания. Пауза темпа JSONL отделена от времени обработки.

## Оценка

EvaluationRun содержит серверный JSON-отчёт. Категории, приоритеты, язык и needs_human оцениваются независимо, только по реально заполненным меткам. Исходный lang — эвристика и не считается эталоном. Исторические verdict/punishment/violation не подменяют категорию. Существование ссылки и человеческая проверка её релевантности — разные показатели. Качество черновика и KK/UZ ожидают ручных оценок, если их не предоставили.
